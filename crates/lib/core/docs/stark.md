
## miden::core::stark
| Procedure | Description |
| ----------- | ------------- |
| verify | Verifies a STARK proof.<br /><br />Generic verifier used by relation-specific wrappers. It expects the following parameters on the<br />stack from the caller:<br /><br />1. `[D0, D1, D2, D3, D4]` which are the digests for dynamic execution of:<br />D0. `observe_aux_trace`<br />D1. `process_public_inputs`<br />D2. `process_row_ood_evaluations`<br />D3. `execute_constraint_evaluation_check`<br />D4. `compute_deep_composition_polynomial_queries`<br /><br />Before calling this procedure, a relation wrapper must:<br /><br />- store the transcript-bound security parameters, which this procedure validates;<br />- store its relation digest, preprocessed commitment at `PREPROCESSED_TRACE_COM_PTR`, and<br />canonical AIR heights; and<br />- supply the five hooks listed above in the documented ABI order.<br /><br />The relation's ACE READ vector must place the lookup challenges at `AUX_RAND_ELEM_PTR` and<br />its first OOD row at `OOD_EVALUATIONS_PTR`. ACE alignment slots must be zero, as in a fresh<br />execution context. Its query row must fit from `CURRENT_TRACE_ROW_PTR` up to the FRI query<br />reservation at `FRI_COM_PTR - 4 * NUM_QUERIES_MAX`. The relation generator checks these extents.<br /><br />Relation-dependent constants live under `sys/<relation>`. The circuit digest and circuit shape<br />must be derived by regeneration, while any hand-written copy must be pinned to that source.<br /><br />LOG_TRACE_LENGTH_PTR must contain the maximum checked AIR log height, at least<br />LOG_FINAL_DEGREE - 1, so fold-by-four reaches one of the two remainder specializations.<br /><br />Protocol parameters:<br /><br />- Blowup factor: 8.<br />- FRI folding and remainder bounds: generated in `pcs/fri/parameters.masm`.<br />- Constraint folding, OOD evaluations, and aux-trace values use the quadratic extension field.<br /><br />Rust counterpart: `miden_stark::VerifierInstance::verify`. Rust checks PCS openings<br />before evaluating constraints; this procedure evaluates constraints first. Constraint evaluation<br />does not change the Fiat-Shamir transcript, so the order of challenges is the same.<br /><br />Inputs:  [D0, D1, D2, D3, D4]<br />Outputs: [num_queries, query_pow_bits, deep_pow_bits, folding_pow_bits]<br /> |
